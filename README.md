# Celinaz Worship

A worship-services web app for Celinaz — fully independent from `celinaz-attendance` (own repo, own database, own deployment).

## Status: early scaffold

Stack mirrors `celinaz-attendance`'s conventions: Next.js 16 (App Router), React 19, Tailwind v4, NextAuth v5 (credentials + JWT sessions), Drizzle ORM + Neon Postgres, deployed on Vercel.

What exists so far:
- Config files (`package.json`, `tsconfig.json`, `next.config.ts`, Tailwind/ESLint/Drizzle configs)
- `src/auth.ts` — NextAuth credentials provider (email/password, roles: `admin`, `leader`)
- `src/db/schema.ts` — only `users` + `password_reset_tokens` so far (auth infra only)
- `src/db/index.ts` — Neon/Drizzle client
- `src/proxy.ts` — route protection (this Next.js version renamed `middleware.ts` → `proxy.ts`; see `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md` after `npm install`)
- `src/app/sign-in/page.tsx` — sign-in page shell (still needs `sign-in-form.tsx` and `actions.ts`)

## Not yet decided: what the app actually does

We have not yet defined the domain schema (services, songs/sets, volunteer teams, roles, attendance — whatever it turns out to be). The plan was to base this on the owner's existing Mac Numbers spreadsheet (multiple tables), exported to `.xlsx`, but that file has not been shared yet.

**Next step when picking this back up: ask the user for that `.xlsx` export (or ask what the app should manage) before building any domain-specific schema/pages.** Everything built so far is generic auth/infra scaffolding that doesn't depend on that answer.

## Working conventions carried over from celinaz-attendance

- This Next.js version has breaking changes vs. training data — read `node_modules/next/dist/docs/` before writing Next.js-specific code, once `node_modules` exists.
- `AGENTS.md`/`CLAUDE.md` agent-rules block is auto-generated by `next dev` — don't hand-write it, just let it appear and commit it.
